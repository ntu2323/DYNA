### DYNA details

DYNA is `protocols/src/ionia/dyna/` (`bench/replica -m dyna`): multi-partition deadline-ordered replication (N = 2f+1 servers, server *i* leads partition *i*). It uses `~/bench/dynaconfig` and `~/bench/trace.micro` (1000 keys) — the bench picks a **uniformly random key per request**. Replicas execute committed writes into the harness **SplinterDB** (`IONIA_DB_MODE=splinter` default, 256MB cache / 2GB disk like IONIA's helper, `use_log=0`, no fsync — durability comes from f+1 replication; `IONIA_DB_MODE=memory` for lib's in-memory store); the client retransmits (`DYNA_RESEND_TIMEOUT_MS`, default 30ms) and replicas answer retries from an at-most-once reply cache.

**Setup:** deploy your local tree via `--rsync-from` or push to GitHub first:

```bash
SSH_USER=nathantu SSH_KEY_FILE=~/.ssh/corfu_remote python3 setup_dyna_cluster.py \
  --hosts-file cluster_hosts.json --rsync-from /path/to/Ionia
```

**Run (open-loop Poisson):** client concurrency is **`--threads` / `-j`** (bench threads **per sender**; default **`1`**). The sweep script runs `run_cluster_bench.py` once per value in `--threads`.

```bash

  --hosts-file cluster_hosts.json \
  -n 0 \
  -e 150 \
  -w 5 \

  --offered-ops-per-sec 0 \
  --max-inflight 0 \
  --replica-wait-sec 20
# Defaults not shown (unchanged unless set): open-loop load (omit --closed-loop);
# --run-id / --results-dir auto; remote clean each run (omit --no-clean-remote);
# --poisson-rate 60 if omitted (~6000 offered ops/s per sender at -j 1).

# Thread sweep — runs one bench per -j value; default sweep list is 1 2 4 8
SSH_USER=nathantu SSH_KEY_FILE=~/.ssh/corfu_remote \
python3 run_throughput_sweep.py \

# Sweep writes results/sweep_dyna_<id>/t<threads>/ and sweep.csv
```

| Flag | Default | Meaning |
|------|---------|---------|
| `-j` / `--threads` | `1` | Client threads **per sender** (`bench/client -j`) |
| `-n` / `--num-ops` | `0` | Max submissions (`0` = unlimited in open-loop) |
| `-e` / `--experiment-sec` | `60` | Measured window after warmup |
| `-w` / `--warmup-sec` | `5` | Warmup before measured window |
| `--interval-ms` | `1000` | Throughput sample interval (`bench/client -i`) |
| `--trim-pad-sec` | `3.0` | Aggregator trims this many seconds from each end |
| `--poisson-rate` | `60` | Open-loop: mean reqs per 10 ms **per sender** (~`rate×100` ops/s at `-j 1`) |
| `--offered-ops-per-sec` | `0` | If `>0`, use `-G` instead of `--poisson-rate` (precise offered load) |
| `--max-inflight` | `0` | Open-loop outstanding cap per sender (`0` = unlimited) |
| `--replica-wait-sec` | `20` | Sleep after starting replicas before clients |
| `--threads` (sweep only) | `1 2 4 8` | List of `-j` values to run sequentially |


`prepare_cluster.py` (idempotent) does what a fresh CloudLab node needs before DYNA numbers
mean anything:
- **Host tuning** (`remote/tune_node.sh`): `performance` governor, C-states deeper than C1
  off. Deep C-states added ~30 µs to every packet on c6320 (ping RTT 64 → 33 µs).
- **`/mydata/dyna` on receivers** (`remote/prepare_data_disk.sh`): the Ubuntu image's root
  fs is ext3, which SplinterDB can't use (no fallocate → `clockcache_get_internal`
  assertion at replica start). Formats the first *completely blank* disk as ext4 (never a
  disk with partitions / a filesystem signature); not in fstab, so re-run after a reboot.
  `start_dyna_replica.sh` runs the replica from `/mydata/dyna` when it exists.
- **Clock sync** (`sync_cluster_clocks.py` → `clock_sync.sh`): chrony by default; the
  master serves its own clock (no internet upstream — that left the master 414 µs off its
  followers). `--clock-mode ptp` uses hardware PTP (ptp4l + phc2sys) instead; both measured
  ~1.6 µs worst pairwise on c6320.
- **Verification** (`check_clock_sync.py`): measures pairwise `CLOCK_REALTIME` offsets with
  UDP probes (min-RTT filtered) and fails above `--max-offset-us` (default 10). Run it any
  time; it does not trust the daemons' own offset reports.

**Check node health once per reservation.** On the Clemson c6320 reservation one node
(node1) ran at 1.64 GHz vs 2.49 GHz on the rest (hardware cap; same OS settings): as a
replica it went late on ~95% of requests and dragged the whole cluster into the slow path.
Compare `sudo perf stat -e cycles taskset -c 7 python3 -c 's=0
for i in range(2000000): s+=i*i'` (look at the GHz) across nodes, and keep slow nodes as
senders.

After a DYNA run the script prints every view-change line from the replica logs and each
sender's per-interval throughput; a normal run should show **no** `view change: pausing`
(otherwise the failure detector fired falsely — the replica log's `rX suspects rY: silent …
(own tick gap …)` line says whether the peer or the suspecting server stalled).

**Diagnosing performance:**
- `DYNA_STATS=1` (replicas + clients): one line per second. Replica: `busy` (time inside
  message handlers, summed over receive threads), `hmax`, messages/s by type, arrivals
  `on`-time / `lateL` (late at leader, re-timestamped) / `lateF` (late at follower, silent),
  deadline `slack` / `late` / release-loop `relLag`, executor lock time + passes, lock
  waits (`muWait`, `dedupWait`, …), heartbeat / tick gaps, buffer sizes. Distributions print
  `avg/max/nCOUNT` (µs). Client: fast vs slow commits (and why), resends, latency per path.
  Most-late arrivals at one replica = that replica (or its node) is the bottleneck.
- `profile_replicas.py --delay-sec 35 --duration-sec 5 --out prof/` in a second terminal
  during a run: per-thread CPU and hottest symbols on every receiver (installs perf).
- `DYNA_RX_THREADS=N` (replicas): N receive threads (SO_REUSEPORT). Measured *worse* at
  N=4 today (contention on the ordering lock), so keep 1 unless that changes.

### DYNA failover (recovery / rejoin)

```bash
# kill -9 replica 1 at +10s (survivors must install view 1)
python3 run_cluster_bench.py --protocol dyna --hosts-file cluster_hosts.json -e 30 \
  --kill-replica 1 --kill-at-sec 10
# ...and restart it at +15s (it rejoins; everyone must install view 2)
python3 run_cluster_bench.py --protocol dyna --hosts-file cluster_hosts.json -e 30 \
  --kill-replica 0 --kill-at-sec 10 --restart-at-sec 15
```

Times are seconds after the clients launch. The restart keeps `dyna-vr-<idx>.state` (so it
rejoins) and deletes `splinterdb.db`; the pre-kill log is kept as
`replica-<idx>.killed.log`. The run exits non-zero if the expected views weren't installed.
To stress the recovery transfer size (M / rejoin snapshot, currently plain UDP with 9000-byte
fragments), redeploy with a larger key space, e.g. `BENCH_TRACE_NUM_KEYS=100000
python3 setup_dyna_cluster.py ... --skip-build`, and watch for `Sending large` in the replica
logs and for recoveries that stall.

### High-throughput **and** latency (open-loop under load)

Two different goals:

| Goal | Setup | What latency means |
|------|--------|-------------------|
| **RTT / protocol floor** | `--closed-loop` or low `--offered-ops-per-sec` (~`1/RTT`) | Mostly network + consensus |
| **Latency at high offered load** | High `-G` or `--poisson-rate` + **`--auto-max-inflight`** | Includes queueing (intentional load test) |

Without enough inflight capacity, high offered load on WAN stalls the client (0 completions). Use **`--auto-max-inflight`** so `-F` scales with offered rate and planning RTT:

\[
\text{max\_inflight} \approx \text{offered ops/s} \times \text{RTT}_{\text{sec}} \times \text{factor}
\]

(default factor = 4, RTT = 0.35 s for WAN).

**WAN example** (~200 offered ops/s per sender, ~330 ms RTT):

```bash
SSH_USER=nathan python3 run_cluster_bench.py --protocol vr \
  --hosts-file cluster_hosts.json \
  --offered-ops-per-sec 200 \
  --auto-max-inflight --expected-rtt-sec 0.33 \
  -e 150 -w 5 --interval-ms 1000 --trim-pad-sec 10
```

**Same-region / high offered** (e.g. `--poisson-rate 50` → ~5000/s per sender, ~0.5–1 ms RTT):

```bash
SSH_USER=nathan python3 run_cluster_bench.py --protocol dyna \
  --hosts-file cluster_hosts.json \
  --poisson-rate 50 \
  --high-throughput-latency --expected-rtt-sec 0.0008 \
  -e 150 -w 5 --interval-ms 1000 --trim-pad-sec 10
```

(`--high-throughput-latency` enables `--auto-max-inflight`.)

Increase offered rate until throughput plateaus or `max_inflight` is constantly full (enable `BENCH_INFLIGHT_LOG=1` on senders). Compare VR vs DYNA at the **same** `--offered-ops-per-sec` and same `--max-inflight` / `--auto-max-inflight`.

**DYNA env knobs** (defaults in `start_dyna_replica.sh` / `run_dyna_client.sh`; `run_cluster_bench.py` forwards locally-set values). Deadlines use **`system_clock`** (Nezha-style), so senders and replicas should be clock-synced (NTP/PTP).

| Env | Where | Meaning |
|-----|--------|---------|
| `DYNA_INITIAL_BOUND_US` / `DYNA_MAX_OWD_US` | both | Cold-start deadline bound / OWD clamp (μs); deadline = send + bound |
| `DYNA_OWD_PERCENTILE` / `DYNA_OWD_WINDOW_LEN` | replica | Percentile and window of per-client OWD samples fed back to clients |
| `DYNA_BUSY_POLL` | both | `1` (default) busy-poll transport + release loop; `0` = epoll / cv park (use on clients at high `-j`) |
| `DYNA_RESEND_TIMEOUT_MS` | client | Retransmit interval (default 30) |
| `DYNA_SLOW_TIMEOUT_US` | client | All leaders replied but quorum short → force slow path after max(this, 3×bound) µs (default 2000; raise on WAN) |
| `DYNA_TS_SCAN_MS` / `DYNA_TS_TIMEOUT_MS` | replica | Background tick (ts-agreement, prepare re-broadcast, stale-commit re-ack, executor backstop; default 50ms) / SPECULATIVE age before ts-agreement (default 100ms) |
| `DYNA_FAIL_TIMEOUT_MS` | replica | Recovery: a peer silent this long is suspected → view change (default 1000; `0` disables failure detection — no false view changes under extreme load) |
| `DYNA_FAIL_GRACE_MS` / `DYNA_HB_MS` | replica | Allowance for a peer never heard from since start (default 10000; also how long a whole-cluster restart waits before starting fresh) / heartbeat + VR tick period (default 20) |
| `DYNA_VR_STATE_DIR` / `DYNA_SNAPSHOT_CHUNK` | replica | Where `dyna-vr-<idx>.state` (persisted view; its presence at startup ⇒ rejoin) lives (default cwd; the dyna cleanup removes it) / key-values per rejoin catch-up chunk (default 512) |
| `DYNA_DEBUG=1` | both | Log request / reply / quorum flow (verbose) |
| `BENCH_INFLIGHT_LOG=1` | client | Adds `inflight=` and `submitted=` to throughput interval lines |

**DYNA vs VR latency (same open-loop bench):** VR replies as soon as the leader path completes; DYNA intentionally holds each request until its deadline (`send + bound`) before the SpecReply, then commits on an f+1 quorum that includes every involved partition leader. Closed-loop sanity: `--closed-loop` with one sender should land near **bound + RTT**.
