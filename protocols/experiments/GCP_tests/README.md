# GCP bench cluster (VR & DYNA)

3 receivers + 1+ senders. Commands run from this directory.

**Prereqs:** `pip install -r requirements-deploy.txt`, `secrets/gcp_secrets.py` (GCP service account + GitHub deploy key for [ntu2323/IONIA](https://github.com/ntu2323/IONIA)), firewall **UDP 31880** between VMs.

```bash
export SSH_USER=nathan
export SSH_KEY_FILE=~/.ssh/id_ed25519   # optional
cd Ionia/protocols/experiments/GCP_tests
```

`cluster_hosts.json` and `secrets/` are gitignored.

**Trace:** write-only `trace.micro` with **1000 distinct keys** (Insert/Update alternating; client cycles the list when `-n 0`). Generated by `bench_trace.py` on deploy. **Load:** open-loop Poisson by default (Nezha-style, ~`--poisson-rate × 100` offered ops/s per sender). Use `--closed-loop` for legacy send-after-ack behavior.

---

## 1. Create cluster (once)

```bash
pip install -r requirements-deploy.txt
python3 create_cluster.py 4 --hosts-file cluster_hosts.json
```

**Default (no flags):** all VMs use `deploy_vm.ZONE` (`us-east4-c`) — no zone overrides passed to `create_vm`.

**Wide-area (1 RTT DYNA vs 2 RTT VR):** `--spread-replica-zones` places receivers in `EXTRA_REPLICA_ZONES` and senders in `EXTRA_CLIENT_ZONE` (edit both at the top of `create_cluster.py`):

```bash
python3 create_cluster.py 4 --hosts-file cluster_hosts.json --spread-replica-zones
```

`cluster_hosts.json` records `receiver_zones`, `extra_client_zone` (when spread), and `spread_replica_zones`. Ensure firewall **UDP 31880** allows replica traffic between those zones (and from senders).

## 2. Setup VMs

Run **one protocol at a time** (VR/DYNA use UDP port 31880; IONIA uses 31880 internal + 31850 client, matching the canonical IONIA CloudLab harness). First install on all VMs uses full deps; day-to-day use **`--skip-build`** after pushing to GitHub.

Protocols: **`vr`** = paxos/src NOPaxos VR baseline; **`dyna`** = ionia/src `-m dyna`; **`ionia`** = ionia/src `-m vr` (VRReplica + VRDurabilityReplica — the IONIA system, *not* the `vr` baseline). `dyna` and `ionia` share the same `protocols/src/ionia` build.

### First time (full build)

```bash
# VR (paxos baseline)
SSH_USER=$SSH_USER python3 setup_paxos_vr_cluster.py --hosts-file cluster_hosts.json

# DYNA (after VR or instead of VR — not in parallel)
SSH_USER=nathantu SSH_KEY_FILE=~/.ssh/corfu_remote python3 setup_dyna_cluster.py --hosts-file cluster_hosts.json

# IONIA (ionia -m vr; two-config layout)
SSH_USER=nathantu SSH_KEY_FILE=~/.ssh/corfu_remote python3 setup_ionia_cluster.py --hosts-file cluster_hosts.json
```

Optional: `IONIA_GIT_REF=my-branch` for a non-default branch. Local tree without push: `--rsync-from /path/to/Ionia` (skips git clone).

### After code changes (`--skip-build`)

Skips apt, Folly, Splinter/RocksDB bootstrap. Still runs **`git pull`** (or uses rsync tree) and **`make bench/replica bench/client`** so edits like `replica.cc` are recompiled.

```bash
# Push to GitHub first, then:
SSH_USER=nathantu SSH_KEY_FILE=~/.ssh/corfu_remote python3 setup_paxos_vr_cluster.py --hosts-file cluster_hosts.json --skip-build
SSH_USER=nathantu SSH_KEY_FILE=~/.ssh/corfu_remote python3 setup_dyna_cluster.py --hosts-file cluster_hosts.json --skip-build
SSH_USER=nathantu SSH_KEY_FILE=~/.ssh/corfu_remote python3 setup_ionia_cluster.py --hosts-file cluster_hosts.json --skip-build

# Or rsync local Ionia without push:
IONIA_REPO_ROOT=/path/to/Ionia SSH_USER=$SSH_USER python3 setup_dyna_cluster.py \
  --hosts-file cluster_hosts.json --skip-build --rsync-from "$IONIA_REPO_ROOT"
```

Logs: `~/paxos_vr_setup.log` / `~/dyna_setup.log` / `~/ionia_setup.log` on each VM. Success markers: `~/bench/.setup_paxos_done` / `.setup_dyna_done` / `.setup_ionia_done`.

## 3. Run benchmarks (from laptop)

Stop the other protocol’s replicas before switching (VR ↔ DYNA ↔ IONIA).

### Orchestrated (recommended)

SSH_USER=nathan python3 run_cluster_bench.py \
  --protocol dyna \
  --hosts-file cluster_hosts.json \
  --ssh-user nathan \
  -e 90 \
  -w 10 \
  --interval-ms 1000 \
  --trim-pad-sec 3 \
  -j 1 \
  -n 0 \
  --poisson-rate 40 \
  --replica-wait-sec 8



`run_cluster_bench.py` starts replicas, launches clients in the background, waits, fetches logs. Each run **clears remote bench state by default** (stops old processes, `rm ~/bench/runs/*` on senders, VR `rm /dev/shm/rocks{idx}`, DYNA `rm` the active WAL dir — `~/bench/wal` or `/dev/shm/dyna-wal` with `--wal-tmpfs`). Use `--no-clean-remote` only if you need to preserve state for debugging.

```bash
# VR — open-loop default (~6000 offered ops/s with --poisson-rate 60)
SSH_USER=nathan python3 run_cluster_bench.py --protocol vr --hosts-file cluster_hosts.json \
  -e 150 -w 5 --interval-ms 1000 --trim-pad-sec 10 --poisson-rate 30

# DYNA — same defaults
SSH_USER=nathan python3 run_cluster_bench.py --protocol dyna --hosts-file cluster_hosts.json \
  -e 150 -w 5 --interval-ms 1000 --trim-pad-sec 10 --poisson-rate 30


SSH_USER=nathantu SSH_KEY_FILE=~/.ssh/corfu_remote python3 setup_ionia_cluster.py


# IONIA (ionia -m vr, UDP FastTransport) — open-loop.
SSH_USER=nathantu SSH_KEY_FILE=~/.ssh/corfu_remote python3 run_cluster_bench.py --protocol ionia --hosts-file cluster_hosts.json \
  -e 150 -w 5 --interval-ms 1000 --trim-pad-sec 10 --poisson-rate 30

# DYNA — WAL on tmpfs (fsync triage: if mean/p99 drop sharply, disk fsync is the bottleneck)
SSH_USER=nathantu SSH_KEY_FILE=~/.ssh/corfu_remote python3 run_cluster_bench.py --protocol dyna --hosts-file cluster_hosts.json \
  --wal-tmpfs -e 150 -w 5 --interval-ms 1000 --trim-pad-sec 10 --poisson-rate 30

# Tune offered load (rate = mean reqs per 10ms; ~rate×100 ops/s per sender)
SSH_USER=$SSH_USER python3 run_cluster_bench.py --protocol dyna --hosts-file cluster_hosts.json \
  --poisson-rate 100 -e 90 -w 5 --interval-ms 1000

# Legacy closed-loop (send after each completion; -n caps total ops)
SSH_USER=$SSH_USER python3 run_cluster_bench.py --protocol dyna --hosts-file cluster_hosts.json \
  --closed-loop -n 100000 -e 90 -w 5 --interval-ms 1000

# Aggregate
python3 aggregate_bench_results.py results/<run_id>

# Thread sweep
SSH_USER=$SSH_USER python3 run_throughput_sweep.py --protocol dyna --threads 1 4 8 -e 120
```

| Flag | Meaning |
|------|---------|
| `-e` | Measured experiment seconds (after warmup) |
| `-w` | Warmup seconds |
| `-n` | Submission cap (`0` = unlimited; default for open-loop) |
| `--poisson-rate` | Open-loop offered load (default `60`) |
| `--closed-loop` | Disable Poisson; wait for ack before next send |
| `--interval-ms` | Throughput log interval (`bench/client -i`) |
| `--no-clean-remote` | Skip wiping remote runs / RocksDB / WAL (default is clean) |
| `--wal-tmpfs` | DYNA only: `DYNA_WAL_DIR=/dev/shm/dyna-wal` on replicas (fsync isolation) |
| `--no-eager-fast-reply` | DYNA only: Nezha deadline hold (default: **eager** fast-reply on admit) |
| `--offered-ops-per-sec` | Open-loop: per-sender offered ops/s (`-G`; use on WAN instead of `--poisson-rate`) |
| `--max-inflight` | Open-loop: cap outstanding requests per sender (`-F`; backpressure) |
| `--wan-open-loop` | Preset: `-G 10`, `-F 500`, no Poisson load during warmup (needs rebuilt `bench/client`) |
| `--auto-max-inflight` | `-F ≈ offered × --expected-rtt-sec × --inflight-factor` (for high-throughput latency) |
| `--expected-rtt-sec` | Planning RTT for auto inflight (default `0.35` WAN) |
| `--high-throughput-latency` | Enables `--auto-max-inflight`; you set offered rate (`-G` or `--poisson-rate`) |

### WAN open-loop (VR or DYNA)

Wide RTT makes `--poisson-rate 50` (~5k offered ops/s per sender) stall the client (0 experiment completions). Use:

```bash
# Rebuild on senders after pulling bench changes:
# setup_*_cluster.py --skip-build  OR  dyna_build_rsync.sh

SSH_USER=nathan python3 run_cluster_bench.py --protocol vr \
  --hosts-file cluster_hosts.json --wan-open-loop -e 150 -w 5 --interval-ms 1000

# Tune offered load (per sender); rule of thumb: start near 1/RTT_sec ops/s
SSH_USER=nathan python3 run_cluster_bench.py --protocol vr \
  --offered-ops-per-sec 10 --max-inflight 500 -e 150 -w 5 --interval-ms 1000
```

Open-loop changes: **no submissions during warmup**; optional **max inflight**; **`-G`** for fractional offered rates (not limited to `-R` ≥ 1 = 100 ops/s).

### High-throughput **and** latency (open-loop under load)

Two different goals:

| Goal | Setup | What latency means |
|------|--------|-------------------|
| **RTT / protocol floor** | `--closed-loop` or low `--offered-ops-per-sec` (~`1/RTT`) | Mostly network + consensus |
| **Latency at high offered load** | High `-G` or `--poisson-rate` + **`--auto-max-inflight`** | Includes queueing (intentional load test) |

Without enough inflight capacity, high offered load on WAN stalls the client (0 completions). Use **`--auto-max-inflight`** so `-F` scales with offered rate and planning RTT:

\[
\text{max\_inflight} \approx \text{offered ops/s} \times \text{RTT}_{\text{sec}} \times \text{factor}
\]

(default factor = 4, RTT = 0.35 s for WAN).

**WAN example** (~200 offered ops/s per sender, ~330 ms RTT):

```bash
SSH_USER=nathan python3 run_cluster_bench.py --protocol vr \
  --hosts-file cluster_hosts.json \
  --offered-ops-per-sec 200 \
  --auto-max-inflight --expected-rtt-sec 0.33 \
  -e 150 -w 5 --interval-ms 1000 --trim-pad-sec 10
```

**Same-region / high offered** (e.g. `--poisson-rate 50` → ~5000/s per sender, ~0.5–1 ms RTT):

```bash
SSH_USER=nathan python3 run_cluster_bench.py --protocol dyna \
  --hosts-file cluster_hosts.json \
  --poisson-rate 50 \
  --high-throughput-latency --expected-rtt-sec 0.0008 \
  -e 150 -w 5 --interval-ms 1000 --trim-pad-sec 10
```

(`--high-throughput-latency` enables `--auto-max-inflight`.)

Increase offered rate until throughput plateaus or `max_inflight` is constantly full (enable `BENCH_INFLIGHT_LOG=1` on senders). Compare VR vs DYNA at the **same** `--offered-ops-per-sec` and same `--max-inflight` / `--auto-max-inflight`.

Results:

```text
results/<run_id>/
  run_meta.json
  sender1/client.log
  summary.json
```

### Manual (SSH)

**Receivers:**

```bash
~/bench/start_paxos_vr_replica.sh 0    # VR on receiver1 (index 0)
~/bench/start_dyna_replica.sh 0        # DYNA
~/bench/start_dyna_replica.sh 0 --wal-tmpfs   # DYNA, WAL on tmpfs
```

**Sender (open-loop example):**

```bash
cd ~/Ionia/protocols/src/ionia
./bench/client -s ~/bench/dynaconfig -c ~/bench/dynaconfig -m dyna \
  -k ~/bench/trace.micro -O -R 60 -n 0 -e 90 -w 5 -t 1 -j 1 -i 1000 -l ~/bench/latencies
```

Helpers: `~/bench/run_paxos_vr_client.sh`, `~/bench/run_dyna_client.sh` (update these if you want open-loop flags baked in).

**DYNA slow-path logs:** `~/bench/start_dyna_replica.sh` sets `DYNA_SLOWPATH_DEBUG=1` by default (logging only; does not force slow path). After a bench run, on each receiver: `grep "DYNA slowpath" ~/bench/replica-*.log`. Disable with `DYNA_SLOWPATH_DEBUG=0` before starting a replica. Re-run `setup_dyna_cluster.py --skip-build` to refresh the helper on existing VMs. Deadlines use **`system_clock`** (Nezha-style), not per-VM `steady_clock`, so senders and replicas should agree under GCP NTP.

**DYNA performance stats (default on via setup helpers):**

| Env | Where | Meaning |
|-----|--------|---------|
| `DYNA_STATS=1` | replica | Every `DYNA_STATS_INTERVAL_SEC` (default 1s): queue depths, release/slowpath rates, sampled `queue_us` / `hold_us` / `fastQ_us` |
| `DYNA_STATS_SAMPLE` | replica | Sample 1/N releases for latency breakdown (default 1024) |
| `DYNA_CLIENT_STATS=1` | client | Every `DYNA_CLIENT_STATS_LOG_EVERY` completions (default 10000): total / first-reply / quorum-wait μs percentiles |
| `BENCH_INFLIGHT_LOG=1` | client | Adds `inflight=` and `submitted=` to throughput interval lines |

Replica lines: `grep "DYNA stats" ~/bench/replica-0.log`. Client lines are in `runs/<id>/client.log`; `aggregate_bench_results.py` pulls `per_sender_diagnostics` (max inflight, client phase p50s) into `summary.json`. Disable any flag with `=0`.

**Replication tuning (defaults in `start_dyna_replica.sh`):** `DYNA_REPLICATION_BUDGET` (normal dequeue batch, default 256), `DYNA_REPLICATION_BURST_BUDGET` (batch when `replQ` ≥ threshold, default 8192), `DYNA_REPLICATION_BACKLOG_THRESHOLD` (default 1000). Sync/fsync/`SendMessageToAll` run **outside** `partitionMu_` so the process thread can release FastReplies while replication catches up.

**DYNA vs VR latency (same open-loop bench):** VR replies as soon as the leader path completes (no hold-until-`deadline_us`); DYNA intentionally waits until **`now >= send_us + bound_us`** before `FastReply`. With correct OWD on GCP, **`bound_us` should be ~100–500 μs** (`DYNA_INITIAL_BOUND_US` / `DYNA_MAX_OWD_US` on replicas and senders via `start_dyna_replica.sh` / `run_dyna_client.sh`). Closed-loop sanity: `--closed-loop` with one sender should land near **bound + quorum RTT** (sub–few ms), not tens of ms. Open-loop at high offered load on a **small keyspace** adds per-key queueing on top of that floor; the default trace uses **1000 keys** so `-R 30` is closer to a defensible paper setup. If closed-loop is fast but open-loop median is still very high, look at pipeline/threading before deadline math.

**Deadline env (GCP defaults in setup helpers):** `DYNA_INITIAL_BOUND_US=500`, `DYNA_MAX_OWD_US=10000`, `DYNA_BOUND_RECOMPUTE_K=1`, `DYNA_FAST_REPLY_SHARDS=16` (UDP send parallelism for FastReply).
